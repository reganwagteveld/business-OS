# CI and merge pipeline optimisation — measurements, design and owner decisions

**Status:** Direction approved by Regan on 2026-11-16 (decisions D-CI-1 to D-CI-5, §9). This document is documentation only: it changes no workflow, branch protection, merge process or production setting. Each phase (§8) is implemented in its own PR, which needs a ChatGPT audit and Regan's merge approval.
**Measured:** 2026-11-16 16:30 UTC, `main` at `0e7e1d9`, all 357 runs of `.github/workflows/ci.yml` since 2026-11-13, with job and step timings sampled from recent runs.

## 1. Summary

CI itself is not slow per run: a pull request run takes **6–8 minutes**, and jobs start within seconds even at peak. Throughput is lost to **how many runs we start and how the merge loop serialises them**:

- **42% of today's pull request runs (63 of 149) were started by a "merge main into branch" commit**, mostly to keep branches up to date while `main` moved 30 times in one day.
- **Docs-only PRs ran the full suite**: 49 runs today (about 256 runner-minutes) for changes that cannot affect code. Docs PRs averaged 5.8 runs each, against 3.7 for code PRs.
- **One serial step decides every run's length**: integration tests run file by file in the Database job (3.5–5.5 min), followed by seven suites re-run behind PgBouncer (≈2 min). Everything else finishes in under 1.5 minutes.
- **Each queued merge costs about 16 minutes** today: sync, about 7 minutes of PR CI, merge, then about 8 minutes of `main` CI before the next one.

The proposal: sync branches only at the head of the merge queue, give docs-only and client-only changes a smaller (still fail-closed) gate, split the Database job into parallel shards, and let the queue skip blocked PRs without ever skipping approval. Estimated effect: **about half the CI runs, a 3–3.5 minute critical path for full runs (from 6–8), about 1 minute for docs PRs, and roughly 3× queue throughput.** Nothing in tenant isolation, auth, finance, migration or security testing is removed or weakened: every full run still runs every suite, including every pooler suite.

## 5. Design (direction approved 2026-11-16)

### 5.1 Parallel development and one serialized merge coordinator

- **Developers do not sync with `main` while developing.** A branch merges `main` only when (a) GitHub reports a conflict, (b) the work depends on something newly merged, or (c) **the PR reaches the head of the merge queue**. This removes most of D1.
- **The merge-queue thread owns the final sync.** At the head of the queue it merges `main` into the branch (never rebase or force-push), waits for the full `CI gate` on that exact commit, verifies the gate ran the expected tier (§5.8), merges, and records the result.
- **Pipelining:** while `main`'s post-merge run for PR *k* is in progress, the queue may sync PR *k+1* and start its gate. It **merges** PR *k+1* only after PR *k*'s `main` run is green and the deploy/smoke check passed. If `main` goes red, the queue halts (as today).
- **Native GitHub merge queue:** to my knowledge it is available only to organisation-owned repositories (unverified for this account). Moving the repository to an organisation would give `merge_group` runs and server-side serialisation, but it touches the Vercel and GitHub App installations. That is listed as an option for later, not recommended now.

### 5.2 Automatic cancellation of superseded runs

- Keep the current per-PR `cancel-in-progress` and the never-cancel rule for `main`, tags, manual and scheduled runs.
- Add an explicit `types: [opened, synchronize, reopened, ready_for_review]` so marking a draft ready always starts a fresh run.
- Agents push a batch of commits at once, not commit by commit (protocol note). The 29 cancelled runs today mostly came from rapid successive pushes.

### 5.3 Dependency caching and safe reuse of build outputs

1. **Shard the Database job** (the largest win; approved as D-CI-3). The job becomes four parallel jobs, each with its own PostgreSQL service, roles, migrations and privileged SQL:
   - `Database integration (1/3, 2/3, 3/3)`: `vitest --shard=i/3` over the same 29 files, still `fileParallelism: false` inside each shard.
   - `Database isolation and pooler suites`: the RLS spike (S1–S13), all seven pooler suites unchanged, and `db:check-migrations`.

   Every test still runs, against a fresh database per shard. Expected critical path: about 50 s setup + about 1.5–2 min, so roughly 3–3.5 min for the whole run (estimated; to be measured in a dry run).

   **Acceptance criteria before adoption (D-CI-3):** each of the four jobs has its own PostgreSQL service, roles, migrations and privileged SQL; a deliberately failing test placed in each shard (and in the pooler job) fails the overall `CI gate`; the set of executed test files and test counts matches the current Database job exactly (compared from vitest output); and measured job and gate durations are reported against the §3 baseline.
2. **Cache Prisma-generated clients and `node_modules` per job.** Key: OS, Node version, `pnpm-lock.yaml` hash, and a hash of every `schema.prisma`. Install still runs `--frozen-lockfile` (fast when nothing changed). Saving ≈10–20 s per job. Low risk, but the key must include the schemas.
3. **Do not reuse test results across commits.** Reusing build outputs across different trees risks false greens, so it is out of scope. One safe form of reuse may come later (Phase 4): the `main` push run could skip jobs whose exact git tree already passed the full tier at the queue head. That needs its own review.

### 5.4 Targeted checks based on affected packages (risk tiers)

Extend `classify-changes.sh` (fail-closed, self-tested) to output a **tier** from the PR's changed files:

| Tier | Paths (every changed file must match) | Jobs that must succeed |
|---|---|---|
| **docs** | `docs/**`, `*.md` outside `.github/` and `apps/*/src/**`, `docs/**` images | Detect changes, a docs check (Markdown link/anchor check), gate |
| **client** | `apps/web/**` (not config), `apps/desktop/src/**`, `packages/ui/**`, `packages/app/**` | Detect changes, static, unit, build, gate (desktop matrix by its existing rule) |
| **full** | anything else, **including** API (`apps/api/**`), contracts (`packages/contracts/**`), database, migrations and privileged SQL, authentication, permissions/RBAC, CI configuration (`.github/**`), dependency changes (lockfile, any `package.json`, `Cargo.*`), root or build config, `tests/**`, `ops/**`, `scripts/**`, any unknown path, an empty or unreadable diff | Everything, including all Database shards and every pooler suite |

**D-CI-2 conditions (approved):** client-only PRs may skip the Database jobs, but must still pass typecheck, lint, boundaries, unit tests, builds, the API-boot and bundle-security checks, and the desktop matrix whenever its existing rule applies. Any change to the API, contracts, database, migrations, authentication, permissions, CI configuration or dependencies, and any unknown change, gets full CI. Classification fails closed, and `CI gate` stays the single required check.

Rules that keep this safe:

- **Fail closed.** Any path not explicitly listed, a mix of tiers, or a classifier error means `full`.
- The gate (`ci-gate.sh`) treats a skipped job as acceptable **only** when the classifier succeeded and reported a tier that does not need it, exactly as the desktop matrix works today. The self-tests cover each tier, mixed changes, unknown paths and an empty diff.
- **Security-sensitive paths always mean `full`**: migrations, privileged SQL, `core/tenant`, auth, admission, RBAC, finance modules, `.github/**`.
- `CI gate` stays the single required check with the same name. Nothing is bypassed: the gate decides, on every run, what was applicable.

Not proposed: running only "affected" integration test files on code PRs. Module-to-test mapping is error-prone in a multi-tenant codebase, and sharding already gives most of the speed-up with every test still running.

### 5.5 A complete, mandatory final merge gate appropriate to risk

- Tier comes from the **diff against the base**, not from draft status or labels, so it is the same whether a PR is draft or ready and cannot be lowered by hand.
- At the queue head the branch is up to date, so the final gate tests the exact tree that will land on `main`.
- **Full tier = today's complete suite, plus the shards.** Nothing that runs today is dropped from the full tier.
- Migration PRs keep the existing order (read production `_prisma_migrations`, recovery branch, apply with Regan's approval, verify, then merge). The queue never merges a migration PR before the migration is recorded as applied.
- The gate summary prints the tier and the reason, so the coordinator and the auditor can see what ran.

### 5.6 A streamlined docs-only path

- Docs tier: CI in about 1 minute instead of 6–8.
- Docs PRs skip pre-queue syncs entirely. At the queue head they still merge `main` if GitHub requires an up-to-date branch. That costs about 1 minute, not about 7.
- The approval rules do not change: ChatGPT audit and Regan's merge approval still apply. Docs PRs that change process rules (`CLAUDE.md`, the protocol, the registry) are flagged in the queue table.
- Shared docs that conflict often (for example `active-workstreams.md`) stay single-writer, as today.

### 5.7 A queue that skips blocked PRs without bypassing approval

The queue is ordered by priority (security first, then dependency order). At each step the coordinator takes the **first eligible** PR, not simply the first PR. A PR is eligible only if all of these hold:

1. Not a draft, or Regan explicitly approved "ready and merge" for it.
2. ChatGPT audit sign-off is recorded for the current head, ignoring sync merges from `main`.
3. **Regan's explicit merge approval** is recorded, with a link to his message. The approval covers that PR's content. A conflict-free sync merge from `main` keeps it, but new commits or a conflict resolution send the PR back for re-audit and re-approval.
4. Any migration or privileged SQL is applied and verified, with its own approval.
5. No `hold` label and no open blocker in the queue table.

Blocked PRs keep their priority slot and return to the head as soon as they become eligible. **Skipping only means "pass over for now". It never means "merge without".** The queue halts entirely, as today, on a red `main`, a failed smoke check, an unexpected conflict, or a security-sensitive surprise.

### 5.8 Visibility

- **Queue table**, kept by the merge-queue thread and mirrored to the pinned GitHub issue: PR, tier, priority, audit, Regan approval (link), migration state, last CI result and duration, queue position, blocker, merge status and time.
- **Pinned issue and labels** (approved as D-CI-4): one pinned "Merge queue" issue, and labels `queue:eligible`, `queue:blocked`, `queue:merging` and `queue:held`. The issue shows each PR's audit status, Regan's approval, CI state, blockers and queue position. **Labels and the issue are informational only. They never stand in for Regan's explicit approval**, which is always a message of his.
- **Gate summary** (already prints per-job durations) adds: tier and reason, critical-path duration, shard durations, and whether the run tested an up-to-date merge with `main`.
- **Weekly metrics** in the queue thread, read from the Actions API: runs per merged PR, share of sync runs, gate p50/p90, re-run count, approval-to-merge time.

## 6. Estimated savings

These are estimates from 2026-11-16's volume. They are not guarantees, and each phase gets measured after rollout.

| Change | Mechanism | Estimate |
|---|---|---|
| Sync only at queue head (§5.1) | About one sync run per merged PR instead of 63 today | −35 to −45 PR runs/day (≈25–30%) |
| Docs tier (§5.4, §5.6) | About 1 min instead of 6–8 per docs run | −200 to −250 run-min/day; docs iterations 6× faster |
| Client tier (§5.4) | No Database job for client-only PRs | Client-only runs ≈2 min instead of 6–8 |
| Database shards (§5.3) | Critical path 6.5 min → ≈3–3.5 min | Every full run ≈50% faster |
| Queue pipelining (§5.1) | Overlap `main` verification with the next PR's gate | Queue cycle ≈16 min → ≈5–6 min per PR |
| Caches (§5.3) | Prisma clients and `node_modules` | ≈1–1.5 job-min per run; small wall-clock gain |

Combined: about half as many runs, and full-gate wall time about halved. Most of the gain in merge throughput comes from the queue changes, because they remove waiting on CI that did not need to run.

## 7. Risks and mitigations

| Risk | Mitigation |
|---|---|
| The tier classifier lets code through on the docs or client tier | Fail closed. An allow-list of paths, never a deny-list. Mixed changes become `full`. Self-tests cover each boundary. `.github/**` changes always mean `full`. The gate re-checks the tier. |
| Shards hide a test that depended on another file's leftover state | Each shard gets a fresh database, and a dry run on a test branch must pass all shards. Hidden order dependencies become visible failures, not false greens. |
| More parallel jobs hit the concurrency limit (free plan: 20 jobs) | A full run goes from 6 to 9 Linux jobs. Fewer runs (§5.1) more than offset this. Watch queue waits in the gate summary. |
| A stale branch merges with a semantic conflict | The queue head always syncs and runs the full gate on the up-to-date tree. The post-merge `main` run remains. |
| Approval drift after a sync | The approval is tied to the PR's content. Only a conflict-free sync from `main` keeps it. Anything else goes back to audit and Regan. |
| A cache poisons a build | Keys include the lockfile and schema hashes. Install still runs `--frozen-lockfile`. No cross-commit reuse of test results. |
| Flaky tests stall the queue | Track re-runs. Fix the tests, never skip them. The queue halts on a red `main`, as today. |

Unchanged by any phase: tenant isolation tests, RLS spike, every pooler suite, auth and admission tests, finance integrity suites, migration order check, `db:check-migrations`, the desktop matrix rules, `CI gate` as the only required check, Regan-only approval, and the production migration procedure.

## 8. Rollout (each phase is its own PR → ChatGPT audit → Regan approval)

Approved sequence (2026-11-16). The phases stay independently reviewable and avoid files owned by active feature PRs. All phases are separate from this PR.

1. **This PR (#94):** documentation only, recording the measurements and the decisions.
2. **Phase 1, process (D-CI-1):** serialized merge queue; no repeated syncs with `main`; sync at the queue head, or earlier only for a genuine dependency or conflict; skip blocked or unapproved PRs without losing priority; ChatGPT audit and Regan's explicit merge approval for every PR; prepare the next PR's CI while the previous merge's `main` verification runs, but never merge it until that verification and the required deployment checks succeed; pinned issue and labels (D-CI-4). Edits `docs/agent-task-protocol.md` and the merge-queue procedure.
3. **Phase 2, workflow (D-CI-2):** docs, client and full tiers in `classify-changes.sh` and `ci-gate.sh` with self-tests, `ready_for_review` trigger, tier in the gate summary, `docs/ci.md` update.
4. **Phase 3, workflow (D-CI-3):** three integration shards plus the RLS/PgBouncer job, meeting the §5.3 acceptance criteria.
5. **Measure** each phase against the §3 baseline before proposing anything further. Phase 4 (caches, `main` tree reuse) is not approved and would need a new proposal.

**Reporting after each phase:** measured CI duration, redundant runs removed, merge throughput, remaining bottlenecks, and any failures or regressions.

**Safeguards for every phase:** never weaken authentication, RLS, tenant isolation, financial integrity, migration or privileged SQL testing; never bypass or fabricate a green `CI gate`; never merge without Regan's explicit approval; production migrations and privileged SQL need their own approval; an unexpected conflict or a substantive code change invalidates earlier sign-off until re-reviewed; a failed `main` CI run or production smoke test halts merging; no production or infrastructure change is authorised by this direction.
