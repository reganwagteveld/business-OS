# Business OS: Initial Data Model (Phase 1)

> Status: **Draft for review.** Schemas below are illustrative design sketches, not migration files. See [architecture.md](./architecture.md) for the isolation model this data model relies on.

## 1. Scope

Phase 1 covers the entities needed for identity, tenancy and the Customer Zone:

| Entity | Module | Tenant-owned? | Purpose |
|---|---|---|---|
| `User` | identity | No (global) | A person who can sign in |
| `Business` | tenancy | Is the tenant | A customer of Business OS (the tenant) |
| `Membership` | tenancy | Yes | Links a user to a business with a role |
| `Invitation` | tenancy | Yes | Pending invite to join a business *(addition, needed to add members)* |
| `Customer` | customers | Yes | A company or individual the business sells to |
| `Contact` | customers | Yes | A person, usually at a customer |
| `Activity` | activity | Yes | A business-facing timeline entry (note, call, system event) |
| `AuditEvent` | core | Yes (nullable for platform events) | Append-only security log *(addition, recommended)* |

Auth provider tables (sessions, OAuth accounts, verification tokens) are owned by the `identity` module and depend on decision D1. They are not tenant-owned.

Out of scope for Phase 1 (deliberately not modelled): deals, invoices, products, projects, employees, custom fields, tags, file attachments, billing.

## 2. Conventions

| Convention | Rule | Why |
|---|---|---|
| Primary keys | `id uuid` UUIDv7, generated by the app or `uuidv7()` on PostgreSQL 18 | Non-guessable, time-ordered (good index locality), safe to expose in URLs |
| Tenant key | `business_id uuid NOT NULL` on every tenant-owned table | Basis for scoping, RLS and composite FKs |
| Tenant-safe uniqueness | Every tenant table has `UNIQUE (business_id, id)` | Target for composite foreign keys |
| Foreign keys between tenant tables | Composite `(business_id, x_id) → x(business_id, id)` | Database refuses cross-tenant references |
| Indexes | Every tenant index leads with `business_id` | All queries are tenant-filtered; RLS predicate uses it |
| Timestamps | `created_at`, `updated_at` as `timestamptz`, UTC | Unambiguous across business time zones |
| Authorship | `created_by_id`, `updated_by_id` → `users.id` (nullable for system) | Who did what, without needing the audit log |
| Archiving | `archived_at timestamptz NULL` on user-facing records | Business "delete" is reversible; hidden from default lists |
| Hard delete | Only for GDPR erasure or business deletion, via a dedicated service | Keeps a single, audited path for irreversible removal |
| Naming | Prisma models PascalCase, mapped to snake_case plural tables (`@@map`) | Readable SQL for RLS policies and reporting |
| Emails | Stored lower-cased; global uniqueness only on `users.email` | Customer contacts may legitimately share or duplicate emails |
| Enums | Postgres enums only for stable, closed sets (role, customer kind); free text + zod validation for evolving sets (activity type) | Avoids a migration every time an activity type is added |
| Money | Not in Phase 1. When added: integer minor units + ISO 4217 currency code | Recorded now so nobody uses floats later |

## 3. Entity relationships

```
               ┌──────────┐
               │   User   │ (global)
               └────┬─────┘
                    │ 1..*
               ┌────▼───────┐        ┌────────────┐
               │ Membership │ *────1 │  Business  │ (tenant root)
               └────────────┘        └─────┬──────┘
                                           │ 1..* (business_id on everything below)
       ┌─────────────┬──────────────┬──────┴───────┬───────────────┐
  ┌────▼─────┐ ┌─────▼────┐  ┌──────▼─────┐ ┌──────▼─────┐ ┌───────▼────┐
  │Invitation│ │ Customer │  │  Contact   │ │  Activity  │ │ AuditEvent │
  └──────────┘ └────┬─────┘  └─────┬──────┘ └──┬──────┬──┘ └────────────┘
                    │ 0..1      *  │           │      │
                    └──────────────┘           │      │
                    Customer 1──* Contact      │      │
                    Customer 1──* Activity ────┘      │
                    Contact  1──* Activity ───────────┘
```

- A user has many memberships; a business has many memberships. `(business_id, user_id)` is unique.
- A contact belongs to **zero or one** customer (decision D5). A contact without a customer is allowed (e.g. a lead or a supplier contact before the relationship is defined).
- An activity relates to a customer, a contact, both, or neither (a business-level event).

## 4. Entities

The Prisma sketches below use the multi-file schema layout from the architecture doc. Field-level comments explain non-obvious choices.

### 4.1 User (identity, global)

```prisma
model User {
  id            String    @id @default(uuid(7)) @db.Uuid
  email         String    @unique              // lower-cased on write
  emailVerified Boolean   @default(false)
  name          String?
  imageUrl      String?
  locale        String?                        // UI preference, e.g. "en-AU"
  timeZone      String?                        // IANA, e.g. "Australia/Perth"
  createdAt     DateTime  @default(now()) @db.Timestamptz
  updatedAt     DateTime  @updatedAt @db.Timestamptz
  deactivatedAt DateTime? @db.Timestamptz      // platform-level lockout

  memberships   Membership[]
  @@map("users")
}
```

- Not tenant-owned: a user exists independently and can join several businesses.
- **No RLS** on `users`, but the `identity` module only exposes: the current user, and users who share a membership with the current business (for "assigned to" pickers). Listing all users is a platform-admin operation, not available to tenant code.
- Exact columns depend on D1; with Better Auth this table is shared with the auth library.

### 4.2 Business (tenancy, tenant root)

```prisma
model Business {
  id           String    @id @default(uuid(7)) @db.Uuid
  name         String
  slug         String    @unique               // URL segment; changeable, never used as an identity
  legalName    String?
  countryCode  String?   @db.Char(2)           // ISO 3166-1 alpha-2
  timeZone     String    @default("UTC")       // IANA; drives "today" in the UI
  locale       String    @default("en")        // formatting, D7
  currency     String    @default("USD") @db.Char(3) // ISO 4217 default for future money fields
  createdAt    DateTime  @default(now()) @db.Timestamptz
  updatedAt    DateTime  @updatedAt @db.Timestamptz
  archivedAt   DateTime? @db.Timestamptz       // business closed; data retained for the retention window

  memberships  Membership[]
  @@map("businesses")
}
```

- RLS on `businesses` uses `id` instead of `business_id`: a request can only see its own business row. Creating a business and listing "my businesses" for the switcher go through dedicated `tenancy` services that run before a tenant context exists, using a narrowly-scoped query on `memberships` by `user_id`.
- Slugs are reserved against a deny-list (`settings`, `api`, `admin`, …) and are resolved through membership on every request, so knowing a slug grants nothing.

### 4.3 Membership (tenancy)

```prisma
enum MembershipRole { OWNER ADMIN MEMBER }
enum MembershipStatus { ACTIVE SUSPENDED }

model Membership {
  id          String           @id @default(uuid(7)) @db.Uuid
  businessId  String           @db.Uuid
  userId      String           @db.Uuid
  role        MembershipRole   @default(MEMBER)
  status      MembershipStatus @default(ACTIVE)
  createdAt   DateTime         @default(now()) @db.Timestamptz
  updatedAt   DateTime         @updatedAt @db.Timestamptz

  business    Business @relation(fields: [businessId], references: [id], onDelete: Cascade)
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([businessId, userId])
  @@unique([businessId, id])
  @@index([userId])                       // "which businesses am I in?"
  @@map("memberships")
}
```

- Invariant enforced in the `tenancy` service (and a deferred constraint trigger): **every active business has at least one active OWNER.** Removing or demoting the last owner fails.
- Removing a member deletes the membership row (with an `AuditEvent`); their authored records keep `created_by_id` for history.
- Future custom roles: add `roleId` → `roles(business_id, id)` alongside `role`, migrate, then drop the enum (see architecture §7.2).

### 4.4 Invitation (tenancy)

```prisma
model Invitation {
  id           String          @id @default(uuid(7)) @db.Uuid
  businessId   String          @db.Uuid
  email        String                          // lower-cased
  role         MembershipRole  @default(MEMBER)
  tokenHash    String          @unique         // store a hash; the raw token is only in the email link
  invitedById  String          @db.Uuid
  expiresAt    DateTime        @db.Timestamptz // e.g. 7 days
  acceptedAt   DateTime?       @db.Timestamptz
  revokedAt    DateTime?       @db.Timestamptz
  createdAt    DateTime        @default(now()) @db.Timestamptz

  @@unique([businessId, id])
  @@index([businessId, email])
  @@map("invitations")
}
```

- Acceptance requires the signed-in user's **verified** email to match `email`.
- Accepting runs before a tenant context exists, so lookup by `tokenHash` is a dedicated, audited service path, not general tenant code.

### 4.5 Customer (customers)

```prisma
enum CustomerKind { COMPANY INDIVIDUAL }

model Customer {
  id             String       @id @default(uuid(7)) @db.Uuid
  businessId     String       @db.Uuid
  kind           CustomerKind @default(COMPANY)
  displayName    String                         // what the UI shows and searches
  legalName      String?
  email          String?                        // general inbox, e.g. accounts@
  phone          String?                        // E.164 when parseable, else as entered
  website        String?
  taxNumber      String?                        // ABN/VAT/EIN; format varies by country
  addressLine1   String?
  addressLine2   String?
  city           String?
  region         String?
  postalCode     String?
  countryCode    String?   @db.Char(2)
  notes          String?                        // short free text; longer history goes in Activity
  ownerUserId    String?   @db.Uuid             // account owner within the business
  primaryContactId String? @db.Uuid
  createdById    String?   @db.Uuid
  updatedById    String?   @db.Uuid
  createdAt      DateTime  @default(now()) @db.Timestamptz
  updatedAt      DateTime  @updatedAt @db.Timestamptz
  archivedAt     DateTime? @db.Timestamptz

  contacts       Contact[]

  @@unique([businessId, id])
  @@index([businessId, displayName])
  @@index([businessId, archivedAt])
  @@map("customers")
}
```

- **Address as columns, not a separate table**, for Phase 1. A customer with multiple addresses (billing vs shipping) is a Finance/Operations concern; when that Zone arrives, an `addresses` table can be introduced and these columns migrated into it. Tradeoff: simpler now, one migration later.
- `ownerUserId` must reference a user with a membership in the same business. Enforced by composite FK to `memberships(business_id, user_id)` rather than to `users`, so the database guarantees it.
- `primaryContactId` uses a composite FK to `contacts(business_id, id)` and is `DEFERRABLE` (customer and first contact are often created together).
- Search in Phase 1: `ILIKE` plus a `pg_trgm` GIN index on `(display_name)` and contact names/emails. Full-text or external search is deferred until there is a measured need.

### 4.6 Contact (customers)

```prisma
model Contact {
  id           String    @id @default(uuid(7)) @db.Uuid
  businessId   String    @db.Uuid
  customerId   String?   @db.Uuid
  firstName    String?
  lastName     String?
  displayName  String                            // computed on write if not provided
  email        String?                           // lower-cased; not unique
  phone        String?
  mobile       String?
  jobTitle     String?
  notes        String?
  createdById  String?   @db.Uuid
  updatedById  String?   @db.Uuid
  createdAt    DateTime  @default(now()) @db.Timestamptz
  updatedAt    DateTime  @updatedAt @db.Timestamptz
  archivedAt   DateTime? @db.Timestamptz

  customer     Customer? @relation(fields: [businessId, customerId], references: [businessId, id])

  @@unique([businessId, id])
  @@index([businessId, customerId])
  @@index([businessId, email])
  @@index([businessId, displayName])
  @@map("contacts")
}
```

- **Composite relation `[businessId, customerId] → [businessId, id]`** is the cross-tenant safety net described in architecture §7.3, layer 5.
- `onDelete`: archiving a customer does not archive contacts automatically; the UI offers it. Hard-deleting a customer sets `customer_id` to null via `ON DELETE SET NULL (customer_id)` (PostgreSQL 15+ column-list form, so `business_id` is not nulled). This is hand-written in the migration because Prisma cannot express it.
- **Decision D5 tradeoff:** one customer per contact is simple and covers most SMB cases. A many-to-many `contact_customers` link (a consultant who works with two clients) is a non-breaking addition later. Choosing many-to-many now costs complexity on every screen for a minority case.
- Duplicate detection (same email in one business) is a soft warning in the UI, not a constraint.

### 4.7 Activity (activity)

The activity timeline is the business-facing history of a record: notes, calls, meetings, emails logged by users, and system events like "Customer created". It is **not** the security audit log.

```prisma
enum ActorType { USER SYSTEM AI }

model Activity {
  id           String    @id @default(uuid(7)) @db.Uuid
  businessId   String    @db.Uuid
  type         String                           // "note" | "call" | "meeting" | "email" | "customer.created" | ...
  occurredAt   DateTime  @db.Timestamptz        // when it happened (user may back-date a call)
  actorType    ActorType @default(USER)
  actorUserId  String?   @db.Uuid               // null for SYSTEM
  customerId   String?   @db.Uuid
  contactId    String?   @db.Uuid
  subject      String?                          // short title
  body         String?                          // plain text / markdown; sanitised on render
  data         Json      @default("{}")         // type-specific payload, validated by a zod schema per type
  schemaVersion Int      @default(1)            // version of the payload schema for `type`
  createdAt    DateTime  @default(now()) @db.Timestamptz
  updatedAt    DateTime  @updatedAt @db.Timestamptz
  deletedAt    DateTime? @db.Timestamptz        // user-entered activities can be removed; system ones cannot

  customer     Customer? @relation(fields: [businessId, customerId], references: [businessId, id])
  contact      Contact?  @relation(fields: [businessId, contactId],  references: [businessId, id])

  @@unique([businessId, id])
  @@index([businessId, customerId, occurredAt(sort: Desc)])
  @@index([businessId, contactId, occurredAt(sort: Desc)])
  @@index([businessId, occurredAt(sort: Desc)])
  @@map("activities")
}
```

**How an activity links to its subject: options considered**

| Option | Integrity | Growth as Zones are added | Query simplicity |
|---|---|---|---|
| **A. Explicit nullable FK per subject type** (`customer_id`, `contact_id`, later `deal_id`, `invoice_id`…) | Real composite FKs, tenant-safe | One column + index per new subject type | Simple |
| B. Polymorphic `subject_type` + `subject_id` | None (no FK possible) | No schema change | Simple, but orphaned and cross-tenant references possible |
| C. Link table `activity_links(activity_id, subject_type, subject_id)` | None for the subject side | No schema change | Joins for every timeline |

**Recommendation: A for Phase 1.** It keeps database-enforced tenant integrity, which is worth more than schema flexibility while there are only two subject types. Revisit when the number of subject types passes roughly five; option C with per-type link tables (`activity_deals`, `activity_invoices`) keeps FKs at that point.

Other rules:

- A `CHECK` that `actor_user_id` is non-null when `actor_type = 'USER'` and null when `actor_type = 'SYSTEM'`.
- System activities are written **in the same transaction** as the change they describe (architecture §5.2, rule 5).
- An activity tied to a contact that belongs to a customer also sets `customer_id`, so the customer timeline includes contact-level history without a join through contacts. Kept consistent by the `activity` service.
- `type` is free text validated against a registry in code (each module registers its activity types with a zod schema for `data`), not a Postgres enum, so new types do not need migrations.
- **No mock activity.** Timelines start empty; the empty state explains how activity appears.

### 4.8 AuditEvent (core)

```prisma
model AuditEvent {
  id          String   @id @default(uuid(7)) @db.Uuid
  businessId  String?  @db.Uuid                  // null for platform events (e.g. sign-in)
  actorUserId String?  @db.Uuid
  action      String                             // "membership.role_changed", "customer.exported", ...
  targetType  String?
  targetId    String?  @db.Uuid
  metadata    Json     @default("{}")            // no customer PII
  ipAddress   String?                            // retention-limited
  userAgent   String?
  createdAt   DateTime @default(now()) @db.Timestamptz

  @@index([businessId, createdAt(sort: Desc)])
  @@index([actorUserId, createdAt(sort: Desc)])
  @@map("audit_events")
}
```

- **Append-only:** the app role is granted `INSERT` and `SELECT` only (no `UPDATE`/`DELETE`).
- Activity vs audit: Activity answers "what happened with this customer?" for business users. AuditEvent answers "who changed permissions or exported data?" for owners and for security investigation. They overlap a little by design; merging them would mix PII-bearing business content with a security log that has different retention and access rules.

## 5. Row-Level Security

### 5.1 Roles

```sql
-- Owner role: runs migrations, owns tables. Never used by the running app.
CREATE ROLE bos_owner LOGIN;
-- App role: what the application connects as. Not owner, no BYPASSRLS.
CREATE ROLE bos_app LOGIN NOBYPASSRLS;
GRANT USAGE ON SCHEMA public TO bos_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON customers, contacts, activities, memberships, invitations TO bos_app;
GRANT SELECT, INSERT ON audit_events TO bos_app;
```

### 5.2 Policy pattern (applied to every tenant table)

```sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;
ALTER TABLE customers FORCE ROW LEVEL SECURITY;   -- applies even to the table owner

CREATE POLICY tenant_isolation ON customers
  USING      (business_id = current_setting('app.business_id', true)::uuid)
  WITH CHECK (business_id = current_setting('app.business_id', true)::uuid);
```

- `current_setting(..., true)` returns null when unset, so `business_id = NULL` is never true: **no context means no rows**, and inserts are rejected.
- `businesses` uses `id = current_setting('app.business_id', true)::uuid`.
- Pre-tenant paths (list my memberships, accept invitation, create business) use `SECURITY DEFINER` functions with fixed, minimal queries (e.g. `my_memberships(user_id)`), owned by `bos_owner`, each covered by tests. This is the only sanctioned way around tenant RLS.

### 5.3 Setting the context with Prisma

```ts
// core/db/tenant-client.ts  (illustrative)
export function forTenant(ctx: TenantContext) {
  return basePrisma.$extends({
    query: {
      $allModels: {
        async $allOperations({ model, args, query }) {
          if (!TENANT_MODELS.has(model)) return query(args);
          const scoped = injectBusinessId(model, args, ctx.businessId); // layer 3
          const [, result] = await basePrisma.$transaction([
            basePrisma.$executeRaw`SELECT set_config('app.business_id', ${ctx.businessId}, true)`,
            query(scoped),
          ]);                                                            // layer 4
          return result;
        },
      },
    },
  });
}
```

- Transaction-local `set_config(..., true)` is reset at commit, so pooled connections never carry another tenant's setting.
- Multi-step service operations use an interactive transaction that sets the context once at the start.
- **Must be validated in the Phase 1b spike**: correctness under PgBouncer/provider pooling in transaction mode, behaviour with the chosen Prisma version's driver adapter, and overhead per query (target: < 2 ms p95 added).

## 6. Indexing and performance notes

- Every tenant index leads with `business_id`; this also makes the RLS predicate index-friendly.
- Lists are paginated with keyset pagination on `(business_id, sort_key, id)`, not offset.
- Expected Phase 1 volumes per business (assumption): < 50 users, < 50k customers, < 200k contacts, < 2M activities. A single Postgres instance handles thousands of such tenants comfortably.
- If a single tenant becomes very large, hash partitioning `activities` by `business_id` is the first lever; it does not change application code.

## 7. Privacy and data lifecycle

- **Export:** an owner can export all of a business's data (customers, contacts, activities) as CSV/JSON. Recorded in `audit_events`.
- **Erasure of a contact (GDPR-style request):** a dedicated service hard-deletes the contact, scrubs its personal fields from related activities' `data`, and writes an audit event without the erased PII.
- **Business deletion:** archive first (soft, reversible for a grace period, e.g. 30 days), then a hard-delete job removes all rows with that `business_id`. Backups age out per the provider's retention.
- **Retention:** `audit_events.ip_address`/`user_agent` cleared after a retention window (e.g. 90 days), decision pending with D3 (jurisdiction).

## 8. Data-model open questions

| ID | Question | Current proposal |
|---|---|---|
| D5 | Contact ↔ customer cardinality | Zero or one customer per contact |
| DM1 | Do individual customers need a linked contact, or is the customer record enough? | Customer record is enough; contacts optional |
| DM2 | Should customers have a lifecycle status (lead / active / former)? | Not in Phase 1; it belongs to the Sales Zone design so it's defined once |
| DM3 | Tags and custom fields | Not in Phase 1; a frequent SMB request, design separately to avoid an unindexed JSON dumping ground |
| DM4 | Default business currency/locale on creation | Derived from country chosen at onboarding |
| DM5 | Retention periods for audit data and archived businesses | Depends on D3 jurisdiction |
