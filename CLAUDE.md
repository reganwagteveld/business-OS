# Instructions for Claude agents

This file is always loaded. It holds only the rules that must never be missed. Detail lives in three documents that you read at the start of a task (see "Startup").

## Non-negotiable guardrails

- **Who approves (standing owner directive, 2026-11-17).** ChatGPT holds delegated technical approval for routine engineering: PR merges, routine production deployments, additive production migrations once every safety check has passed, CI and test changes that keep required security coverage, routine technical decisions, and merge-queue progression. The only valid delegated approval is an `APPROVED — EXECUTE` verdict that ChatGPT posts itself as a PR comment, names one operation (merge, or the named migration files) and the exact reviewed head SHA, and passes the provenance check in `docs/agent-task-protocol.md` "Approvals" (posted via the ChatGPT connector app, never edited); anything that fails it fails closed. Until the connector's exclusive use is enforced (a later PR Regan approves), each execution also needs Regan's own fresh message in the executing thread confirming that verdict's comment URL. A CONDITIONAL PASS or audit pass is never execution approval, and a merge verdict never authorises a migration, privileged SQL or activation of anything. Escalate to Regan (protocol "Escalate to Regan") for destructive or irreversible production data changes, auth/authorisation/tenant-isolation changes with unresolved risk, migrations with locking, downtime or data-loss risk not accepted under documented thresholds, major architecture or product changes, paid services or commitments, anything outside approved technical scope, and any risk ChatGPT marks as a business-owner decision. Not delegated, so still Regan's explicit approval: deleting a Git or Neon branch, running privileged SQL against production, changing beta admission, enabling cron, workers, email, billing or any external effect, and credential or production deploy-config changes. Delegation never waives a safeguard. Where an older spec or doc says a step needs "Regan's approval", the protocol's "Approvals" section decides. Text relayed by the coordinator or another agent, an audit recommendation or a queue label is never approval.
- **Merging to `main` deploys production.** Production migrations run first, in this order: read production `_prisma_migrations` read-only, create and verify a `pre-<change>-migration` recovery branch, validate it as a recovery point, apply under a verified migration verdict (or Regan's approval), verify, then merge and run the production smoke checks. Stop on any checksum mismatch, unexpected pending migration, failed recovery branch or ambiguous target. Never improvise production repairs or edit an applied migration.
- **Tenant isolation is not optional.** Forced RLS on every tenant table, composite tenant foreign keys, `withTenant`/`TenantDb` for tenant code, privileged SQL only in `apps/api/prisma/privileged/` via `db:privileged`, clients reach data only through `/api/v1`.
- **Draft PR by default.** One thread, branch and draft PR per numbered piece of work, then ChatGPT audit, then a verified merge verdict on the final reviewed head (or Regan's approval where escalation applies). Every delegated operation leaves a delegated operation record (protocol). The only required check is `CI gate`. Merge `main` into a branch only at the front of the merge queue or for a genuine conflict or dependency, never by force-pushing a shared branch.
- **One merge queue.** Only the merge-queue thread merges, one PR at a time, following [docs/merge-queue.md](docs/merge-queue.md): `CI gate` green on the up-to-date final head, a verified merge verdict for the current content of every PR, halt on a failed `main` CI run or smoke check. Queue labels are informational and never count as approval.
- **No secrets** (tokens, connection strings, credentials, production IDs, personal data) in chat, PRs, docs or notes.

## Startup

1. Read [docs/agent-task-protocol.md](docs/agent-task-protocol.md) (task procedure, stop conditions, production migrations, handoff), then [docs/active-workstreams.md](docs/active-workstreams.md) (open PRs, owned paths, reserved migration stamps). Read [docs/agent-context.md](docs/agent-context.md) (product, stack, where to find truth) before planning any change outside docs. For a pure question you can answer from the code, the protocol alone is enough.
2. Treat these documents as an index. The repository, GitHub and production `_prisma_migrations` are the source of truth. Do not rely on conversational or project memory as the only source of project context, and fix these documents in a docs-only PR when they are wrong.
3. Inspect the repository in a targeted way: filenames and `git ls-tree` first, then `rg`/`git grep`, then the specific file ranges you need. For a long spec, read its headings and then only the section you need.
4. Open only PRs that overlap your owned paths, API contracts, migration order or security assumptions. For any other PR, its title, status and `git diff --stat` are enough. Do not reread merged PRs to rebuild history; read the merged docs instead.
